# Airports — EARS Specs

Design: [airports-design.md](airports-design.md). Prefix `APT`; facets `DATA` (reference data:
seeding, downloading and importing the lists when the server prepares its airport data at start or
again after a failure, the monthly refresh, requested re-imports, stopping at shutdown), `FIND` (code lookup, search, the airport
input), `NEAR` (nearest airport), `POP` (the airport popup), `RWY` (runway display), `WX` (METAR),
`WIKI` (Wikipedia summaries).

`[x]` implemented · `[ ]` intended, not yet implemented · `[D]` deferred

## Reference Data

- [x] **APT-DATA-001**: When the server prepares its airport data — at start (once it is listening and its start-up work on the logbook is done, and before it starts the sim link — app-shell's start order), or again at a daily check after a failed preparation (APT-DATA-022) — and the database holds no airports, the system shall import the data folder's airport list (`airports.csv`): the one already there, else the one seeded from the program folder (APT-DATA-017), else, with airport downloads on (APT-DATA-020), a downloaded one.
- [x] **APT-DATA-002**: When the server prepares its airport data — at start (once it is listening and its start-up work on the logbook is done, and before it starts the sim link — app-shell's start order), or again at a daily check after a failed preparation (APT-DATA-022) — and the database holds no runways, or no runway that has a heading, the system shall import the data folder's runway list (`runways.csv`): the one already there, else the one seeded from the program folder (APT-DATA-017), else, with airport downloads on (APT-DATA-020), a downloaded one.
- [x] **APT-DATA-003**: While airport downloads are on (APT-DATA-020), when a daily check (run as airport preparation at start ends and every 24 hours after that) finds the last airport preparation — at start, or one repeated under APT-DATA-022 — succeeded, and either airport list (`airports.csv`, `runways.csv`) missing from the data folder or its download time (APT-DATA-018) more than 30 days ago, the system shall download both lists again under temporary names, import them from there, and only once that import has succeeded put them, with their new download times, in place of the data folder's lists.
- [x] **APT-DATA-004**: While the check that app-shell's startup hands to airports reports the pilot in the sim (APP-SRV-012: this server's sim link connected — in the sim's menus and in casual mode included — or the tracker holding a leg in progress, a leg restored at server start and still waiting for the sim included; on the fake feed no sim link is ever connected, so only a leg the feed drives counts), the system shall start no automatic airport-data refresh (APT-DATA-003) and no preparation repeated by a daily check (APT-DATA-022), shall stop one already under way before it replaces any airport data, discarding what it downloaded or staged, and shall start it again from the beginning once the check no longer reports the pilot in the sim.
- [x] **APT-DATA-005**: If an automatic airport-data refresh (APT-DATA-003) fails — a download failing or running out of time (APT-DATA-019), or the import failing — then the system shall leave the data folder's lists, their download times and the imported airport data as they were, and try again at the next daily check.
- [x] **APT-DATA-006**: When the airport list is imported, the system shall replace every airport not retained under APT-DATA-007 in one transaction, skipping airports of type `closed` and rows without numeric coordinates.
- [x] **APT-DATA-007**: When airport data is re-imported, the system shall keep the last-known record and runways of every airport that a hop references and that the new lists omit or mark closed, flagged as no longer listed.
- [x] **APT-DATA-008**: The system shall resolve an airport kept under APT-DATA-007 by its codes like any other airport, and shall not offer it as a planner candidate or return it as a nearest airport.
- [x] **APT-DATA-009**: When the airport popup shows an airport kept under APT-DATA-007, the system shall state "No longer listed by OurAirports".
- [x] **APT-DATA-010**: When the runway list is imported, the system shall replace every runway in one transaction, skipping rows without an airport ident, rounding length and width, storing blank or non-positive lengths and widths as null, and treating lighted and closed as true only for "1".
- [x] **APT-DATA-011**: When a runway is imported, the system shall set each end's heading from the list's true heading normalised to 0–360°, else from a two-digit runway number with an optional L/R/C suffix (number × 10, 36 → 0°), else null, and set a missing high-end heading to the low-end heading + 180°.
- [x] **APT-DATA-012**: When a runway is imported, the system shall classify its surface text as paved, grass, gravel, dirt, water, snow or unknown by testing the upper-cased text against each class's tokens in that order, the first match winning (e.g. ASP, CON → paved; GRS, TURF → grass; GRVL, GRAVEL → gravel; DIRT, SAND → dirt; WATER → water; SNOW, ICE → snow; single letters G, S, C, D → grass, dirt, paved, dirt), and keep the original text.
- [x] **APT-DATA-013**: When the runway list has been imported, the system shall rebuild each airport's runway summary from its open runways only: longest length, widest width, count, distinct surface classes, whether any is paved, whether any is lit, and the distinct rounded headings.
- [x] **APT-DATA-014**: If an airport or runway list lacks a required column, then the system shall fail the import naming the file and the column, and leave the existing data unchanged.
- [x] **APT-DATA-015**: When `npm run import-airports` is run (a development command, run against a copy run from source's database; the installed app refreshes its lists by itself, APT-DATA-003), the system shall re-import both lists, first downloading any list missing on disk, or both lists with `--fresh`.
- [x] **APT-DATA-016**: When `POST /api/airports/reimport` is called, the system shall re-import both lists from disk, first downloading both with `?download=1`, and return the airport and runway counts.
- [x] **APT-DATA-017**: When the server prepares its airport data — at start, or again at a daily check after a failed preparation (APT-DATA-022) — the system shall copy into the data folder, from the program folder (an input of the server's, app-shell; in the installed app, its resources holding the seed airport lists), each airport list (`airports.csv`, `runways.csv`) that the data folder lacks and the program folder holds, under a temporary name put in place only once the copy is complete, writing beside it the download time the program folder's list carries (APT-DATA-018), and shall leave every list already in the data folder, and its time, as it is.
- [x] **APT-DATA-018**: When the system downloads an airport list (`airports.csv`, `runways.csv`) — at start, in a refresh or on request — it shall record the time of that download in a file beside the list named after it with `.downloaded` added (`airports.csv.downloaded`), holding an ISO 8601 UTC date-time ending in `Z` with seconds and optionally fractions of a second (`2026-10-23T14:05:00Z`, `2026-10-23T14:05:00.000Z`) — the form in which the seed lists in the program folder carry theirs (desktop distribution's build scripts) — and shall take a list without that file, or whose file, whitespace around it ignored, holds anything else or a time later than now, to have been downloaded at the list's own last-modified time.
- [x] **APT-DATA-019**: If a download of an airport list receives no data for 60 s, or has not finished within 10 minutes, then the system shall fail that download, and any failed download shall leave the list on disk and its download time as they were.
- [x] **APT-DATA-020**: While the server's airport downloads are off (an input of the server's, app-shell, on by default — the installed app and a copy run from source — and off in the desktop app's test mode and in the Vitest and browser test harnesses), the system shall download no airport list when it prepares airport data (at start, or again after a failure, APT-DATA-022) and run no automatic refresh, preparing airport data only from the lists in the data folder and those seeded from the program folder (APT-DATA-017); a requested re-import (`npm run import-airports`, `POST /api/airports/reimport?download=1`) still downloads.
- [x] **APT-DATA-021**: While the server prepares its airport data — at start, or again at a daily check after a failed preparation (APT-DATA-022) — the system shall keep answering `/api/status` and report in it (app-shell carries the report; its `ready` flag, once set, stays set) the step under way — copying lists from the program folder, downloading a list, or importing airports or runways with the rows imported so far and the total — and, once that preparation has ended, whether it succeeded or failed and why, a repeated preparation's report replacing the earlier one.
- [x] **APT-DATA-022**: If airport preparation — at start, or repeated by a daily check — fails because a list an import needs (APT-DATA-001, APT-DATA-002) is still missing from the data folder after seeding (APT-DATA-017) and may not be downloaded (airport downloads off, APT-DATA-020) or its download fails (APT-DATA-019), or because an import fails, then the system shall end that preparation (at start, so app-shell goes on to start the sim link), keep running with the airport data it had (none on a first run), report what failed and why in `/api/status` (APT-DATA-021), and prepare again at the next daily check after it (checks run as preparation at start ends and every 24 hours after that; the one run as preparation at start ends does not repeat it), held while the pilot is in the sim (APT-DATA-004).
- [x] **APT-DATA-023**: While the system imports an airport or runway list — at start, in a refresh or on request — it shall keep answering requests and keep serving the airport data it had, reading the list and writing its new rows in batches that each hold the server for no more than about 100 ms, between which the server answers requests and takes the sim link's samples, and replacing the old data with the new rows in one short transaction only once the list has been read and checked, so a failure before then leaves the old data unchanged.
- [x] **APT-DATA-024**: While the server is preparing, refreshing or re-importing airport data, the system shall start no other airport import in that server: a daily check falling due meanwhile, or while a refresh or repeated preparation waits for the pilot to leave the sim (APT-DATA-004), does nothing, and `POST /api/airports/reimport` answers HTTP 409 "airport data is already being imported".
- [x] **APT-DATA-025**: When the server shuts down (app-shell's shutdown) while it is seeding, downloading or importing airport lists — at start, in a refresh or on request — the system shall stop the step under way before the database is closed, an import within one batch (APT-DATA-023), discarding that step's unfinished copy, download or staged rows (a list already put in place keeps its download time), so each airport list, its download time and the imported airport data are wholly as before that step or wholly as after it.
- [x] **APT-DATA-026**: When the server prepares its airport data at start, the system shall first remove any temporary airport-list file in the data folder and any airport staging table in the database left by a seed, download or import that an earlier server did not finish.

## Finding Airports

- [x] **APT-FIND-001**: When an airport code is looked up, the system shall match it, trimmed and upper-cased, against the ident, ICAO, GPS, IATA and local codes, preferring an ident match, then ICAO, then GPS, then the others.
- [x] **APT-FIND-002**: When `GET /api/airports/:code` is called, the system shall return the airport with all of its runways, open ones first and then longest first, or HTTP 404 "airport not found: X" when no airport matches.
- [x] **APT-FIND-003**: When airports are searched with a non-blank query, the system shall prefix-match the codes and substring-match the name and city, ranking exact code matches first, then code-prefix matches, then name matches, then by class (large, medium, small, seaplane base, heliport, other), then by name.
- [x] **APT-FIND-004**: When airports are searched, the system shall return nothing for a blank query and cap `GET /api/airports/search` at 1–50 results, 12 by default.
- [x] **APT-FIND-005**: When the user has typed at least two characters in an airport input, the system shall search 120 ms after the last keystroke and show up to 10 results, each with its ident, name, and city and country.
- [ ] **APT-FIND-006**: While an airport input is showing search results, the system shall show only the results for its latest text, discarding responses to earlier text.
- [x] **APT-FIND-007**: While an airport input's result list is open, the system shall move through results with ↑/↓ (wrapping around), pick the highlighted result with Enter, and close the list with Escape.
- [x] **APT-FIND-008**: When the user leaves an airport input or presses Enter with no result list open, the system shall commit the text trimmed and upper-cased.
- [x] **APT-FIND-009**: When an airport input holds a committed code of two or more characters, the system shall show beneath it the airport's name, city and runway summary, or "Unknown airport code" when the code matches no airport.
- [x] **APT-FIND-010**: When an airport input's value is set from outside the input, the system shall replace the text unless the user is typing in it.

## Nearest Airport

- [x] **APT-NEAR-001**: When the nearest airport to a point within a radius is requested, the system shall return the airport within that radius with the lowest distance plus class handicap (large 0, medium 0.3 nm, small 0.8 nm, any other type 2 nm), or none when no airport is within the radius.
- [ ] **APT-NEAR-002**: When the nearest airport to a point within a radius is requested, the system shall consider airports on both sides of the 180° meridian.

## The Airport Popup

- [x] **APT-POP-001**: When the user clicks a visited-airport dot or a planner candidate on the map, the system shall open a popup with "IDENT · Name", the location, the Wikipedia lead image linked to its article when there is one, the runway display with up to five runways, the current METAR when the airport has a station, the Wikipedia extract, and links.
- [x] **APT-POP-002**: The airport popup shall fetch runways, METAR and Wikipedia data only while it is open.
- [x] **APT-POP-003**: When the airport popup opens for an airport known only by its runway summary, the system shall fetch the airport's full runway list.
- [x] **APT-POP-004**: The airport popup shall link to Wikipedia when the airport has an article, the official site when the airport has one (linked as APT-POP-007 says), SkyVector always, and aviationweather.gov's decoded METAR/TAF page when the airport has a METAR station, every link it shows itself, the photo's included, opening as a new window (`target="_blank"`): a new tab in a browser, and the pilot's default browser from the desktop app's window, installed or in test mode (the desktop shell's routing, DESK-SHELL-WIN-007).
- [ ] **APT-POP-005**: When a Wikipedia extract is longer than 260 characters, the airport popup shall cut it at the last sentence end within 260 characters, else at the last word boundary, and append "…".
- [x] **APT-POP-006**: While the airport popup is fetching a METAR it shall show "Fetching METAR…", and when the station has no current report it shall show "No current METAR for X."
- [ ] **APT-POP-007**: When the airport popup links an airport's official site, the system shall take its `home_link` with surrounding whitespace trimmed, use it as given when it is an `http` or `https` address (the scheme in any case), put `https://` in front of a value with no scheme that begins with a host name (two or more labels of letters, digits and hyphens joined by dots, optionally followed by `/` and a path, with no spaces), and show no official-site link for any other value (a value without a scheme would resolve to the page's own address, which the desktop app's window, installed or in test mode, refuses to open as a new window: DESK-SHELL-WIN-007 sends only other origins to the default browser, DESK-SHELL-WIN-008 refuses its own).

## Runway Display

- [x] **APT-RWY-001**: The runway display shall show the airport's class label, its elevation when known, and "no runway data" when the airport has no open runways.
- [x] **APT-RWY-002**: When an airport's runway list is known, the runway display shall list up to the caller's limit of open runways, each with its surface-class color, `LE/HE` name, length or "length n/a", width when known, surface class word, the original surface text when the class is unknown, and "· lit" when lit, followed by "+N more" for open runways beyond the limit.
- [x] **APT-RWY-003**: When only an airport's runway summary is known, the runway display shall show one line of longest length, surface classes and runway count.

## METAR

- [x] **APT-WX-001**: When METARs are requested, the system shall fetch uncached stations from aviationweather.gov in batches of up to 150 and cache each station's result for 5 minutes, caching "no report" as null.
- [x] **APT-WX-002**: When aviationweather.gov returns several reports for one station, the system shall keep the most recently observed.
- [x] **APT-WX-003**: When `GET /api/metar/:icao` is called, the system shall reject a code that is not 4 letters or digits with HTTP 400 and return HTTP 404 "no current METAR for X" when the station reports nothing.
- [x] **APT-WX-004**: When `GET /api/metars?ids=` is called, the system shall drop ids that are not 4 letters or digits, reject the request with HTTP 400 when none remain or more than 500 do, and return null for each station that reports nothing.
- [x] **APT-WX-005**: The system shall take an airport's METAR station to be its ICAO code when that is 4 letters or digits, else its ident when that is 4 letters, else none.
- [x] **APT-WX-006**: The system shall treat a METAR as fresh only when it was observed less than 90 minutes ago, and use only a fresh METAR's flight category (VFR, MVFR, IFR, LIFR) for map graphics and planner flags.
- [x] **APT-WX-007**: When the airport popup shows a METAR, the system shall show the flight-category badge; then wind ("calm", "DIR° N kt", with "GN" for gusts, or "wind n/a"), visibility in SM, the ceiling as the first BKN/OVC/OVX layer ("COVER base ft") or "clear" when there are no cloud layers, temperature/dewpoint in °C, and the altimeter in inHg; then the raw report and "observed N min ago".
- [x] **APT-WX-008**: When a map tooltip summarises a METAR, the system shall show wind, visibility, ceiling (or "clear") and the report's age, separated by " · ".
- [x] **APT-WX-009**: The system shall color flight categories VFR green, MVFR blue, IFR red and LIFR magenta.
- [ ] **APT-WX-010**: When the system stores newly fetched METAR results in its server-memory cache, it shall drop every cached entry more than 5 minutes old, so a server that runs for weeks holds only the stations asked about in the last 5 minutes.

## Wikipedia

- [x] **APT-WIKI-001**: When an airport's Wikipedia summary is requested, the system shall return the title, extract, thumbnail and full image (with tracking parameters removed) and the article URL for the airport's Wikipedia link, or HTTP 404 when the airport has no link or the link is not a wikipedia.org article.
- [x] **APT-WIKI-002**: The system shall cache each airport's Wikipedia summary in the database and reuse it for 30 days.
- [x] **APT-WIKI-003**: If refreshing a Wikipedia summary returns an HTTP error and a cached summary exists, then the system shall return the cached summary.
- [ ] **APT-WIKI-004**: If refreshing a Wikipedia summary fails with a network error or timeout and a cached summary exists, then the system shall return the cached summary.
