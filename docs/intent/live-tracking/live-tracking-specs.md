# Live Tracking — EARS Specs

Design: [live-tracking-design.md](live-tracking-design.md). Prefix `LIVE`; facets `LINK` (sim
link, sim mode, stopping and pausing tracking, and the PC-wide sim-link claim), `LEG` (leg detection and interruptions), `NAME`
(naming the airports), `LAND` (landings and rating), `REC` (what a leg records), `BIND` (binding a
sim aircraft), `HOP` (logging and pending legs), `SAVE` (checkpointing), `CASUAL` (casual mode and
its path), `API` (tracker API and event stream), `CARD` (live card), `LAYER` (live aircraft on the
map), `TOOL` (the development tools sim-fake and sim-probe).

Scope words: **the installed app** is the server bundled for the desktop app as the desktop shell
starts it outside test mode, on the sim link (desktop); **the desktop app's test mode** is the same
server started by the desktop shell with `--test-data=<folder>`, on the fake feed; **a copy run from
source** is the server started from the repository (`npm run dev`, `npm run dev:sim`, `npm start`,
the browser-test server); **the sim mode** is the sim link, the fake feed or off (LIVE-LINK-003,
LIVE-LINK-012, LIVE-LINK-013); **the PC-wide sim-link claim** is the named pipe one server on the PC
holds while linked to the sim (LIVE-LINK-010); **a sim on this PC** is one the link reaches with no
`SIMCONNECT_HOST`, or with one naming this PC (a loopback address, `localhost`, the PC's own name or
one of its own addresses).

`[x]` implemented · `[ ]` intended, not yet implemented · `[D]` deferred

## Sim Link

- [ ] **LIVE-LINK-001**: While the server's sim mode is the sim link, its tracking is neither stopped nor paused (LIVE-LINK-011, LIVE-LINK-017) and, for a link to a sim on this PC, no other server on the PC holds the PC-wide sim-link claim (LIVE-LINK-014; a link to a sim on another PC checks none, LIVE-LINK-015), the system shall connect to the sim and, whenever the sim is unreachable or the connection ends, retry every 10 s, logging only the first failed attempt in a row.
- [x] **LIVE-LINK-002**: While a copy run from source is on the sim link (LIVE-LINK-013, `npm run dev:sim` and `--sim=link` included), when `SIMCONNECT_HOST` is set, the system shall connect to the sim at that host on `SIMCONNECT_PORT`, default 500.
- [x] **LIVE-LINK-003**: While the server's sim mode is the fake feed (LIVE-LINK-012, LIVE-LINK-013), the system shall not connect to the sim and shall take samples from `POST /api/tracker/sample`; while its sim mode is off, the system shall not track at all.
- [x] **LIVE-LINK-004**: While connected to the sim, the system shall read the user aircraft's latitude, longitude, altitude, on-ground flag, ground speed, true heading, vertical speed, indicated airspeed, G, total fuel, total weight, the sim's touchdown velocity, pitch and bank, title, ATC id and livery once a second, stamping each sample with the time it arrived.
- [x] **LIVE-LINK-005**: If the sim rejects the livery variable, then the system shall continue with a blank livery and report liveries as unsupported.
- [x] **LIVE-LINK-006**: When the wheels touch down, the system shall take from the per-frame data the descent rate and airspeed of the last airborne frame and the peak G over the following second, and pass them, with the sim's touchdown velocity as fpm, pitch and bank, on the next once-a-second sample.
- [x] **LIVE-LINK-007**: When the sim reports a pause change, the sim starting or stopping (menus and loading), a flight loaded, or the connection ending, the system shall pass the event to the tracker, telling the sim quitting (SimConnect's quit event, MSFS closing normally) apart from a connection that closed or failed.
- [ ] **LIVE-LINK-008**: While connected to the sim, the system shall read the sim's zulu date and time with each once-a-second sample.
- [x] **LIVE-LINK-009**: If the livery has been neither read nor rejected 5 s after the first sample held on a new sim connection, then the system shall pass the held samples, and those that follow until the livery is read, to the tracker with a blank livery.
- [ ] **LIVE-LINK-010**: While a server on the sim link to a sim on this PC (no `SIMCONNECT_HOST`, or one naming this PC) has its link connected, it shall hold the PC-wide sim-link claim — the named pipe `\\.\pipe\msfs-career-map-sim-link`, which every process on the PC sees — taking it when SimConnect opens, answering each check of it with who holds it (the installed app when the desktop shell started the server, a copy run from source otherwise) and its data folder, and releasing it at once when the link's connection ends or the link stops, its process ending releasing it too.
- [ ] **LIVE-LINK-011**: When the server stops tracking — at its shutdown (app-shell, APP-SRV-016 or APP-SRV-018), or as it pauses tracking to bring in a logbook (LIVE-LINK-017) — the system shall stop the sim link, its per-frame watcher included, with no disconnect or other event reaching the tracker, and release the PC-wide sim-link claim, so the tracker's state saved afterwards is its state from before the link stopped.
- [x] **LIVE-LINK-012**: When the server bundled for the desktop app starts (the installed app, the desktop app's test mode), the system shall take its sim mode from its `--sim` start-up argument alone — `link` the sim link (LIVE-LINK-001), `fake` the fake feed and `off` no tracking (LIVE-LINK-003) — reading none of `TRACKER_FAKE`, `SIMCONNECT_HOST` or `SIMCONNECT_PORT`, and track in that mode (a start without the argument is app-shell's, APP-SRV-006).
- [x] **LIVE-LINK-013**: When a copy run from source starts (`npm run dev`, `npm run dev:sim`, `npm start`, the browser-test server), the system shall take its sim mode from its `--sim` start-up argument when given (`link`, `fake` or `off`, read as LIVE-LINK-012 reads them; `npm run dev:sim` gives `--sim=link`, APP-RUN-019), else the fake feed when `TRACKER_FAKE` is `1`, and off otherwise, and track in that mode.
- [ ] **LIVE-LINK-014**: While another server on the PC holds the PC-wide sim-link claim, a server on the sim link to a sim on this PC shall open no SimConnect connection, checking the claim again at each 10 s retry, a check that finds the pipe held but gets no answer within 1 s counting as held by a holder that does not say who it is; and if, once SimConnect has opened, it cannot take the claim, it shall close that connection at once, passing nothing to the tracker, and wait in the same way.
- [ ] **LIVE-LINK-015**: While the server's sim mode is the fake feed or off, or its sim link reaches a sim on another PC (`SIMCONNECT_HOST` naming another PC), the system shall neither take nor check the PC-wide sim-link claim, and its tracker status shall report `link_holder` null (LIVE-API-013).
- [x] **LIVE-LINK-016**: If the tracker's handling of one sample or sim event throws an error, then the system shall write the error out and keep the server and the sim link running, passing the next sample or event to the tracker as usual.
- [ ] **LIVE-LINK-017**: When the server pauses tracking to bring in a logbook (app-shell, APP-IMP-003), the system shall stop the sim link as LIVE-LINK-011 says and, until tracking resumes, pass the tracker no sample (the fake feed's included) or sim event; when the server resumes tracking after an import that failed before its answer (APP-IMP-003), the system shall start the sim link again when its sim mode is the sim link (LIVE-LINK-001) and pass samples and events on as usual, the tracker going on from its state as it was when tracking paused.
- [x] **LIVE-LINK-018**: If the sim link cannot read a record the sim sends — one shorter than its data definition, which node-simconnect's reader throws on — then the system shall drop that record and keep the connection and the server running, writing out in full the first such record of each data definition on a connection and only counting later ones on that connection, the count written out when the connection ends or the link stops.

## Leg Detection

- [x] **LIVE-LEG-001**: While the sim is paused or not running, the tracker shall ignore samples, and it shall ignore any sample whose position is not finite or lies within 0.05° of both latitude 0 and longitude 0.
- [x] **LIVE-LEG-002**: While casual mode is off, when the aircraft has been off the ground for 5 s after being on the ground, the tracker shall start a leg whose departure time is the first airborne sample and whose track begins at the last on-ground sample.
- [x] **LIVE-LEG-003**: While casual mode is off, when tracking begins with the aircraft already airborne, the tracker shall start a leg with no departure airport.
- [x] **LIVE-LEG-004**: When the aircraft touches down during a leg, the tracker shall mark the leg landed and set its touchdown time.
- [x] **LIVE-LEG-005**: When a landed aircraft leaves the ground again, the tracker shall continue the same leg as airborne and clear its touchdown time.
- [x] **LIVE-LEG-006**: When a landed aircraft has stayed below 5 kt ground speed for 30 s, the tracker shall close the leg at that sample.
- [x] **LIVE-LEG-007**: When the user asks to log a landed leg now (**Log now**, `POST /api/tracker/complete`), the tracker shall close it at the latest sample, and refuse with HTTP 409 when no leg is landed.
- [x] **LIVE-LEG-008**: When the sim link's connection ends while a leg is airborne — the sim quitting or crashing, or the connection failing, never the server stopping the link (LIVE-LINK-011) — other than a leg restored at server start that the sim has not yet resumed (LIVE-LEG-016), the tracker shall keep the leg as a pending leg ending at the last sample, with no destination and the reason "the sim disconnected in flight".
- [x] **LIVE-LEG-009**: When the sim link's connection ends (the sim quitting or crashing, or the connection failing — never the server stopping the link, LIVE-LINK-011), or the sim aircraft's title or livery changes, while a leg is landed, the tracker shall close the leg at the last sample.
- [x] **LIVE-LEG-010**: When the sim aircraft's title or livery changes, a new flight is loaded, or the position jumps more than 50 nm plus 700 kt × the time since the last sample while a leg is airborne — other than a leg restored at server start that the sim has not yet resumed (LIVE-LEG-016) — the tracker shall discard the leg.
- [x] **LIVE-LEG-011**: When a new flight is loaded, or the position jumps more than 50 nm plus 700 kt × the time since the last sample, while a leg is landed, the tracker shall close the leg at the last sample before the event.
- [x] **LIVE-LEG-012**: When the sim link connects, the system shall hold the samples it reads until it has read the livery or the sim has rejected the livery variable, then pass them to the tracker in order with that livery, so a livery not yet read never counts as a change of sim aircraft.
- [ ] **LIVE-LEG-013**: When a closed leg's flight time is under one minute, the tracker shall drop it without logging and leave the current SimBrief briefing for the next leg.
- [ ] **LIVE-LEG-014**: The tracker shall not count time the sim is paused toward the 5 s takeoff confirmation or the 30 s stop.
- [x] **LIVE-LEG-015**: When the user discards the leg being flown, the tracker shall drop it without logging.
- [x] **LIVE-LEG-016**: When the server has restored from its checkpoint a leg in the air, the tracker shall continue that leg only when the first sample it takes from a sim connection shows the same sim aircraft (title and livery), airborne, within 50 nm plus 700 kt × the time since the leg's last sample; otherwise — a new flight loaded before that sample, the sim link's connection ending before it (never the server stopping the link, LIVE-LINK-011), another sim aircraft, a jump beyond that, or the aircraft on the ground — it shall keep the leg as a pending leg ending at its last sample, with no destination and the reason "MSFS Career Map stopped in flight and the sim did not resume it", take that first sample, whenever it comes, as the start of tracking, and never discard the leg or close it as a hop.

## Naming the Airports

- [x] **LIVE-NAME-001**: When a leg starts on the ground, the tracker shall name as its departure the nearest airport within 5 nm of the last on-ground sample, ranked by distance plus class handicap (APT-NEAR-001), or none when there is none.
- [ ] **LIVE-NAME-002**: When a leg starts on the ground with a bound fleet aircraft whose parked airport is within 5 nm of the last on-ground sample and ranks within 1 nm of the nearest airport by distance plus class handicap, the tracker shall name the parked airport as the departure.
- [x] **LIVE-NAME-003**: When a leg closes, the tracker shall name as its destination the nearest airport within 5 nm of where it stopped, ranked as for departures, or none.

## Landings and Rating

- [x] **LIVE-LAND-001**: When the once-a-second samples show a touchdown during a leg and no measured touchdown has arrived within 6 s, the tracker shall record a provisional landing with the descent rate and airspeed of the last airborne sample, no G, and the touchdown position.
- [x] **LIVE-LAND-002**: When a measured touchdown arrives during a leg, the tracker shall replace a provisional landing from within 6 s of it, or else add a new landing, with the measured descent rate, peak G, airspeed, the sim's touchdown rate, pitch, bank and the position.
- [x] **LIVE-LAND-003**: When rating a landing, the system shall take the worse of its descent-rate class (butter up to 100 fpm, solid up to 250, hard up to 500, hospital up to 800, graveyard above) and, when its G is known, its peak-G class (butter below 1.6, solid below 2.0, hard below 2.6, hospital below 3.5, graveyard from 3.5).
- [x] **LIVE-LAND-004**: When a landing is recorded, the tracker shall report "Landed at IDENT: N fpm, rating" or "Landed away from any airport: N fpm, rating", and for a measured touchdown "Touchdown N fpm, G.GG G: rating".

## What a Leg Records

- [x] **LIVE-REC-001**: While a leg is airborne or landed, the tracker shall add a track point at most every 5 s, and add the closing sample when the leg closes, each as `[lat, lon, alt_ft, unix_seconds, gs_kts, vs_fpm, ias_kts, fuel_lb]`.
- [x] **LIVE-REC-002**: When a leg closes, the tracker shall record its real-world departure at takeoff and its arrival at the last touchdown, or at the closing sample when it has not touched down.
- [ ] **LIVE-REC-003**: When a leg closes, the tracker shall record its flight time as the whole minutes from takeoff to arrival, less any time the sim was paused in between.
- [ ] **LIVE-REC-004**: When a leg closes, the tracker shall record its departure and arrival on the sim's clock as well as the real-world clock.
- [x] **LIVE-REC-005**: When a leg closes, the tracker shall record fuel at takeoff and at the closing sample, fuel used, weight at takeoff and at the closing sample, the highest altitude, the highest ground speed and the distance flown along the track, storing a zero fuel or weight reading as unknown.

## Binding a Sim Aircraft

- [x] **LIVE-BIND-001**: When the sim aircraft's title or livery changes, the tracker shall bind it to the fleet aircraft whose sim title matches and whose sim livery matches or is blank, preferring an exact livery and then the oldest aircraft, or to none.
- [x] **LIVE-BIND-002**: When the user binds the sim aircraft to a fleet aircraft, the system shall store the sim title and livery on that aircraft and bind it, refusing with HTTP 400 while there is no sim aircraft and HTTP 404 for an unknown aircraft.
- [x] **LIVE-BIND-003**: When the user binds the sim aircraft to a fleet aircraft, the system shall set that aircraft on every pending leg flown in the same sim title and livery that has no aircraft.

## Logging and Pending Legs

- [x] **LIVE-HOP-001**: When a leg closes with a bound fleet aircraft that still exists and both airports named, the tracker shall log it as a hop at the end of that aircraft's sequence — with its track, landings, statistics, the current SimBrief briefing, and the leg's takeoff time as its `departed_at` exactly as the tracker status gave it (the same ISO UTC string) — and clear the current briefing.
- [x] **LIVE-HOP-002**: When a leg closes without a bound fleet aircraft that still exists, a departure or a destination, the tracker shall keep it as a pending leg with its sim aircraft, everything known, the current SimBrief briefing, and the reason: "no fleet aircraft is bound to this sim aircraft", "the departure airport is unknown" or "no airport within 5 nm of where it stopped".
- [x] **LIVE-HOP-003**: The tracker shall keep pending legs in a list in the order they were kept, never let a new pending leg replace an earlier one, and give each an id unique for the life of the logbook — a random UUID, never a counter that a restored backup or a brought-in logbook could repeat — kept with the leg in the checkpoint.
- [x] **LIVE-HOP-004**: When the user logs a pending leg, the system shall resolve any airport codes given to idents, apply the aircraft and airports supplied, and log it as a hop with the leg's takeoff time as its `departed_at` exactly as the tracker status gave it (the same ISO UTC string, unchanged from the leg in progress to the pending leg to the hop), refusing with HTTP 400 while its aircraft, departure or destination is still missing.
- [x] **LIVE-HOP-005**: When the user discards a pending leg, the system shall drop it, write the checkpoint without it, and only then delete its SimBrief briefing unless a hop uses it.
- [x] **LIVE-HOP-006**: When the tracker logs a hop, it shall report "Logged ORIG → DEST, time" (with "N fpm rating" of the first touchdown of its final landing when it has touchdowns, touchdowns less than 30 s apart being bounces of one landing) and send the hop on the event stream.
- [ ] **LIVE-HOP-007**: The tracker shall mark each pending leg with whether it ended in the air, as `ended_in_air` — true for a leg kept while airborne (the sim link's connection ending in flight, LIVE-LEG-008; a restored leg the sim did not resume, LIVE-LEG-016; a brought-in leg in progress that was airborne, LIVE-SAVE-011) and false for a leg that ended on the ground (closed after landing, LIVE-HOP-002; a brought-in leg in progress that had landed, LIVE-SAVE-011) — and carry the mark with the leg in the tracker status, the `pending` event, `GET /api/tracker/pending/:id` and the checkpoint.

## Checkpointing

- [x] **LIVE-SAVE-001**: The tracker shall save its whole state — casual mode's switch and the time it was switched on included, the casual path never — to the checkpoint (the `tracker_state` row) at most every 5 s while samples arrive, and at once when a leg starts, lands or closes, a landing is recorded or replaced (LIVE-LAND-001, LIVE-LAND-002), a leg is discarded, or the binding, the current briefing, a pending leg or casual mode changes.
- [x] **LIVE-SAVE-002**: When the server starts, the tracker shall restore its saved state, dropping a saved leg that began within 0.05° of latitude 0 and longitude 0, giving a leg saved without landings or statistics empty ones, reading a checkpoint of an older version that holds a single pending leg in place of a list as a list of that one leg, with an id of its own (LIVE-HOP-003), and reading a pending leg saved without `ended_in_air` (LIVE-HOP-007) as ended in the air only when its reason is "the sim disconnected in flight" or "MSFS Career Map stopped in flight and the sim did not resume it".
- [x] **LIVE-SAVE-003**: The tracker shall report whether a leg is in progress.
- [x] **LIVE-SAVE-004**: When the server asks the tracker to save its state now (app-shell's save request, APP-SRV-019, which the desktop shell makes when Windows asks whether the session may end and as the PC suspends), the tracker shall write its whole state to the checkpoint at once and change nothing else.
- [x] **LIVE-SAVE-005**: When the server shuts down (app-shell's shutdown order, APP-SRV-016 or APP-SRV-018), the tracker shall write its final checkpoint after the sim link has stopped (LIVE-LINK-011) and, when the app is quitting (APP-SRV-016), after casual mode has been switched off (LIVE-CASUAL-013), and after it take no sample or sim event and turn down every pilot's action that would change its state (LIVE-API-016), so nothing changes the checkpoint after the final one.
- [x] **LIVE-SAVE-006**: When the tracker logs a hop — from a closed leg (LIVE-HOP-001) or a pending leg (LIVE-HOP-004) — it shall write the hop, its SimBrief briefing's link to it and the checkpoint that no longer holds that leg or pending leg in one SQLite transaction, so a server ended at any instant leaves the flight in the checkpoint or in the logbook, never in both and never in neither.
- [x] **LIVE-SAVE-007**: If the checkpoint cannot be read as a whole when the server starts — not JSON, not a JSON object, its phase missing or unknown, or a field of its own other than the leg in progress present with a type this version cannot read, a pending list that is neither a list nor an object among them (a damaged leg in progress or pending leg being set aside alone, LIVE-SAVE-013, LIVE-SAVE-014, and a field it does not know kept, LIVE-SAVE-012) — then the tracker shall set it aside whole, its text exactly as found, with the time, in the `tracker_state_aside` table, which it never reads again, write that out, and start with an empty state.
- [ ] **LIVE-SAVE-008**: When the server brings in a logbook from another data folder or a backup (app-shell, APP-IMP-002, APP-IMP-003), the tracker shall, once tracking has paused (LIVE-LINK-017), write into the brought-in copy a checkpoint holding this server's own leg in progress, current SimBrief briefing, casual mode and pending legs — the briefings these carry copied into the copy without their fleet aircraft link (it names a row of the logbook being replaced), and those pending legs' fleet aircraft cleared — followed by the source's pending legs (LIVE-SAVE-010) and the source's leg in progress (LIVE-SAVE-011), with the binding of the sim aircraft being flown looked up again in the copy (LIVE-BIND-001).
- [ ] **LIVE-SAVE-009**: If the tracker cannot read the checkpoint of a logbook being brought in (as LIVE-SAVE-007 judges a checkpoint it cannot read), then it shall report that, with the reason, so the logbook is not brought in (app-shell refuses the import, APP-IMP-002).
- [ ] **LIVE-SAVE-010**: When the tracker writes the checkpoint of a logbook being brought in (LIVE-SAVE-008), it shall add, after this server's own pending legs, the source's pending legs it can read (LIVE-SAVE-015) as the source's checkpoint holds them, with their ids, fleet aircraft and SimBrief briefings, which are the copy's own.
- [ ] **LIVE-SAVE-011**: When the tracker writes the checkpoint of a logbook being brought in (LIVE-SAVE-008) and the source's checkpoint holds a leg in progress it can read (LIVE-SAVE-015), it shall add that leg last as a pending leg with an id of its own (LIVE-HOP-003), ending at its last sample, with the source's bound fleet aircraft and the source's current SimBrief briefing, the destination nearest that sample (LIVE-NAME-003) when it had landed and none when airborne, and the reason "brought in from another logbook mid-leg"; and it shall drop the source's current briefing from the copy when no such leg carries it and no hop uses it.
- [x] **LIVE-SAVE-012**: When the tracker restores a checkpoint holding fields this version does not know (written by a later version, before an older one was installed over it), it shall ignore those fields and keep each, unchanged, in every save while the object holding it — the checkpoint, the leg in progress, a pending leg — is kept.
- [x] **LIVE-SAVE-013**: If a pending leg in the checkpoint cannot be read when the server starts — not an object, or lacking or mistyping a field this version needs (`sim` an object with string `title` and `livery`; `departed_at` and `arrived_at` strings; `duration_min` a number; `reason` a string; and, when present, `track` a list, each of its points a list of at least four finite numbers, `landings` a list, each of its touchdowns an object with a string `t`, `stats` an object and `ended_in_air` a boolean) — then the tracker shall set that leg aside alone, its JSON as the checkpoint holds it, with the time, in `tracker_state_aside`, write that out, restore the rest of the checkpoint, and write the checkpoint without that leg at once.
- [x] **LIVE-SAVE-014**: If the leg in progress in the checkpoint cannot be read when the server starts — not an object, or lacking or mistyping a field this version needs (`departed_at` a number and `track` a list, each of its points a list of at least four finite numbers; and, when present and not null, `landings` a list, each of its touchdowns an object with a string `t`, `origin` a string, and `touchdown_at`, `fuel_start_lb`, `weight_start_lb`, `max_alt_ft` and `max_gs_kts` numbers) — then the tracker shall set that leg aside alone, its JSON as the checkpoint holds it, with the time, in `tracker_state_aside`, write that out, restore the rest of the checkpoint with no leg in progress, in the idle phase with no takeoff or stop timer running and no last on-ground or airborne sample, and write the checkpoint without that leg at once.
- [ ] **LIVE-SAVE-015**: When the tracker writes the checkpoint of a logbook being brought in (LIVE-SAVE-008) and the source's checkpoint holds a pending leg or a leg in progress it cannot read (as LIVE-SAVE-013 and LIVE-SAVE-014 judge them), it shall set that leg aside, its JSON as the source's checkpoint holds it, with the time, in the copy's `tracker_state_aside`, and leave it out of the checkpoint it writes.

## Casual Mode

- [x] **LIVE-CASUAL-001**: While casual mode is on, the tracker shall not start, continue or close a leg, measure or rate a landing, or create a pending leg, and shall hold the idle phase with no takeoff or stop timer running and no last on-ground or airborne sample.
- [x] **LIVE-CASUAL-002**: While casual mode is on, the tracker shall still ignore the samples LIVE-LEG-001 ignores, follow the sim aircraft and look up its binding (LIVE-BIND-001) without reporting an unbound one as unbound, report the live position, and leave the current SimBrief plan and any pending legs as they are (no new plan can be imported, SB-CUR-004).
- [x] **LIVE-CASUAL-003**: While casual mode is on, when the tracker takes a sample and the aircraft is not on the ground below 1 kt, the tracker shall add the sample to the casual path as a track point `[lat, lon, alt_ft, unix_seconds, gs_kts, vs_fpm, ias_kts, fuel_lb]` if the path is empty, a break is waiting (LIVE-CASUAL-004), or at least 5 s have passed since the path's last point.
- [x] **LIVE-CASUAL-004**: While casual mode is on, when the position jumps more than 50 nm plus 700 kt × the time since the last sample, a new flight is loaded, or the sim link's connection ends (the sim quitting or crashing, or the connection failing — never the server stopping the link, LIVE-LINK-011), the tracker shall begin a new casual-path segment with the next point it adds.
- [x] **LIVE-CASUAL-005**: When the user switches casual mode on with no leg airborne, the tracker shall close a landed leg at the last sample, logging it or keeping it as pending (LIVE-HOP-001, LIVE-HOP-002), and start casual mode with an empty path.
- [x] **LIVE-CASUAL-006**: If the user switches casual mode on while a leg is airborne in a sim aircraft bound to a fleet aircraft that still exists, and the request does not say to drop the leg (`drop_leg`), then the system shall refuse with HTTP 409 and `{error, aircraft_id, name, origin, departed_at}` naming that fleet aircraft and leg, leaving casual mode off and the leg flying.
- [x] **LIVE-CASUAL-007**: When the user switches casual mode on while a leg is airborne, and its sim aircraft is not bound to a fleet aircraft that still exists or the request says to drop the leg (`drop_leg`), the tracker shall drop the leg without logging it and start casual mode with the leg's track as the casual path's first segment.
- [x] **LIVE-CASUAL-008**: When the user switches casual mode off, the tracker shall drop the casual path and resume leg detection from the idle phase with the next sample it takes (LIVE-LEG-002, LIVE-LEG-003).
- [x] **LIVE-CASUAL-009**: When the user asks to switch casual mode to the state it is already in, the system shall leave casual mode, the casual path and any leg in progress unchanged and answer with the status.
- [x] **LIVE-CASUAL-010**: When the user clears the casual path, the tracker shall empty it and leave casual mode as it is.
- [x] **LIVE-CASUAL-011**: When the server starts without the fresh-run input (LIVE-CASUAL-015) — a restart within a run of the app, or any start of a copy run from source — the tracker shall restore casual mode as its checkpoint holds it — on, with the time it was switched on, or off — with an empty casual path.
- [x] **LIVE-CASUAL-012**: When the user switches casual mode on (LIVE-CASUAL-005, LIVE-CASUAL-007), the tracker shall report "Casual mode on: nothing is logged", adding "; dropped the leg from ORIG" ("?" for an unknown origin) when it dropped a leg; when the user switches casual mode off (LIVE-CASUAL-008), it shall report "Casual mode off: takeoffs and landings are logged again".
- [ ] **LIVE-CASUAL-013**: When the server shuts down because the app is quitting (app-shell: the desktop shell's Shut down over the private channel, APP-SRV-016; never a copy run from source's stop, APP-SRV-018, nor the shutdown that finishes bringing in a logbook, APP-IMP-003), the tracker shall switch casual mode off, dropping the casual path (LIVE-CASUAL-008), before its final checkpoint (LIVE-SAVE-005), so the next server start finds it off.
- [x] **LIVE-CASUAL-014**: When the sim quits cleanly while casual mode is on — SimConnect's quit event, not a connection that closed or failed (LIVE-LINK-007) — the tracker shall switch casual mode off, dropping the casual path, and report "Casual mode off (MSFS closed): takeoffs and landings are logged again".
- [x] **LIVE-CASUAL-015**: When the server starts with the fresh-run input (app-shell's `--fresh-run`, APP-SRV-011, which the desktop shell gives a run's server starts until one of them has done its start-up work), the tracker shall start with casual mode off whatever its checkpoint holds, and write casual mode off into the checkpoint before the server's start-up work is done.

## Tracker API and Event Stream

- [x] **LIVE-API-001**: When `GET /api/tracker` is called, the system shall return the tracker status: link state and the sim's name, whether the sim is running and paused, whether liveries are supported, the sim aircraft and bound fleet aircraft, the phase, the latest position, the leg in progress with its landings, the pending legs, each with its id (LIVE-HOP-003) and without its track, the current briefing, and the last message with its time.
- [x] **LIVE-API-002**: When a client opens `GET /api/tracker/events`, the system shall send the status and the current leg's full track, then the status on every sample and change, each new track point, the full track when a leg starts or ends, each logged hop, each new pending leg, and a keep-alive every 25 s.
- [x] **LIVE-API-003**: The system shall address each pending leg by its own id, logging it with `POST /api/tracker/pending/:id` and discarding it with `DELETE /api/tracker/pending/:id`, and answer HTTP 404 for an unknown id.
- [x] **LIVE-API-004**: If `POST /api/tracker/sample` is called while the server's sim mode is not the fake feed (LIVE-LINK-003), then the system shall refuse it with HTTP 403; otherwise it shall feed the sample to the tracker, first marking the link connected as "fake feed".
- [ ] **LIVE-API-005**: When the page's tracker event stream ends for any reason — an error answer such as the 503 a server gives during its start-up work included — the page shall open it again 3 s later and take the full state the server sends again, and on every reconnect after the first shall reload the map and the lists (as LIVE-CARD-009 does, without its toast), leaving the planner's results and its hand-off to the hop form to the planner (PLAN-RUN-006); a server of another version is app-shell's (APP-UI-036).
- [ ] **LIVE-API-006**: While a leg is in progress, the tracker status shall carry the leg's statistics so far: fuel and weight at takeoff, fuel used, the highest altitude and ground speed, and the distance flown along the track.
- [x] **LIVE-API-007**: When `GET /api/tracker/pending/:id` is called, the system shall return that pending leg in full, with its track, landings, statistics and briefing, and answer HTTP 404 for an unknown id.
- [x] **LIVE-API-008**: When `PUT /api/tracker/casual` is called with `on` true or false, the system shall switch casual mode to it (LIVE-CASUAL-005 to LIVE-CASUAL-009), saying to drop an airborne leg when `drop_leg` is true, and answer with the status; it shall refuse any other `on` with HTTP 400.
- [x] **LIVE-API-009**: When `DELETE /api/tracker/path` is called, the system shall clear the casual path (LIVE-CASUAL-010) and answer with the status.
- [x] **LIVE-API-010**: The tracker status shall carry casual mode as the time it was switched on and the casual path's point count over all segments, or null while casual mode is off.
- [x] **LIVE-API-011**: The tracker event stream shall send the casual path as `path` — a list of segments of track points, empty while casual mode is off — on connect after the status and the leg's track, and again when casual mode switches, the path is cleared or a new segment begins, by then holding that segment's first point; and it shall send each point added to the last segment as `path-point`.
- [x] **LIVE-API-012**: When switching casual mode on drops a leg, the tracker event stream shall send the empty leg `track` before the `path` holding the leg's track, and the status last.
- [ ] **LIVE-API-013**: The tracker status shall carry the server's sim mode as `sim_mode`: `"link"`, `"fake"` or `"off"` (the sim mode's `--sim` values, LIVE-LINK-012, LIVE-LINK-013); the host of a sim on another PC its link reaches as `sim_host`, a string, null for a sim on this PC or no link; and, while a server on the sim link to a sim on this PC finds the PC-wide sim-link claim held by another server (LIVE-LINK-014), that holder as `link_holder`: `{holder, data_folder, text}`, `holder` being `"installed"` or `"source"` as the holder says, or null when it does not say, `data_folder` its data folder when it gives one, else null, and `text` the words "The sim is linked to another copy (the installed app)", "The sim is linked to another copy (run from source)" or, when the holder does not say, "The sim is linked to another copy" — and `link_holder` null otherwise.
- [x] **LIVE-API-014**: The tracker event stream shall send each logged hop as `hop` carrying `{hop, message}` — the hop's record, with its id, and the tracker's message for it (LIVE-HOP-006) — and each leg kept as pending as `pending` carrying that leg as the status lists it: its id, sim aircraft, reason and everything known, without its track.
- [ ] **LIVE-API-015**: While tracking is paused to bring in a logbook (LIVE-LINK-017), the system shall refuse every tracker request that would change the tracker's state — binding, logging or discarding a pending leg, **Log now**, discarding the leg being flown, switching casual mode, clearing the casual path, posting a sample — with HTTP 409 and `{"error": "Bringing in a logbook"}`, and answer the requests that only read — the status, a pending leg in full, the event stream — as usual.
- [ ] **LIVE-API-016**: While the server shuts down after the tracker's final checkpoint (LIVE-SAVE-005), the system shall refuse every request for a pilot's action that would change the tracker's state — switching casual mode, binding, importing or removing the current SimBrief plan (`POST` and `DELETE /api/tracker/briefing`), discarding the leg being flown, **Log now**, logging or discarding a pending leg — with HTTP 503 and `{"error": "MSFS Career Map is shutting down"}`, ahead of the route's own answers (validation, lookups, casual mode's 409, the SimBrief fetch) but after LIVE-API-015's 409 (tracking paused to bring in a logbook), the server's request checks (app-shell, APP-API-011, APP-API-012) and a body it cannot read refusing the request itself, changing nothing, and answer every other tracker request as usual.
