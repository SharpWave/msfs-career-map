# App Shell — EARS Specs

Design: [app-shell-design.md](app-shell-design.md). Prefix `APP`; facets `SRV` (the server: its
inputs, start order, start-up work, the private channel, shutting down, exits and errors, serving),
`DATA` (the data folder, the database, schema upgrades, the logbook's id, one server per data
folder), `BAK` (backups), `IMP` (bringing in a logbook from another data folder or a backup), `API`
(API conventions, request checks, `/api/status`, the version), `UI` (page layout, menu and drawers,
the covered part of the map, failures, starting, the hand-off fragment, reloading for a new version or another logbook, the look), `FMT` (shared
formatting), `RUN` (development scripts and the test harness).

Modes the specs name: **the installed app** (the server bundled into the desktop app, started by
the desktop shell outside test mode), **the desktop app's test mode** (the same server, started with
`--test-data=<folder>`), **a copy run from source** (`npm run dev`, `npm run dev:sim`, `npm start`,
the browser-test server) and **the test servers** (the app `createApp` builds, on a free port, in the
Vitest API tests, taking its inputs as APP-SRV-023 says). **A server started as a process** is any
but the test servers. **The program folder** is laid out as `page/` (the page build) beside the seed
airport lists `airports.csv` and `runways.csv` with their `.downloaded` times (APP-SRV-006).

`[x]` implemented · `[ ]` intended, not yet implemented · `[D]` deferred

## Server

- [ ] **APP-SRV-001**: When the server starts — in the installed app, the desktop app's test mode or a copy run from source — the system shall, in this order: listen on 127.0.0.1 at its port (APP-SRV-005) and answer `/api/status` (APP-API-004) with its start-up step `opening`, writing to its output the address, the data folder, the sim and the version; do its start-up work on the logbook — take the data folder's lock (APP-DATA-007), finish bringing in a logbook (APP-IMP-004), open the database, put a restored backup's icons in place and give the logbook its id (APP-BAK-011, APP-DATA-006), back it up and upgrade it when the schema step would change it (APP-BAK-010), and have the tracker restore its checkpoint (live-tracking, LIVE-SAVE-002) — and set its start-up step to `done`; prepare airport data (airports, APT-DATA-001, APT-DATA-002, APT-DATA-017); and, only once that preparation has ended, succeeded or failed, start the sim link when its sim input is the sim link (live-tracking, LIVE-LINK-001).
- [x] **APP-SRV-002**: The server shall serve the API under `/api`, accepting JSON bodies up to 8 MB, and uploaded aircraft icons under `/images` with a one-year immutable cache.
- [x] **APP-SRV-003**: The server shall serve the built page — from the `page` folder of its program folder (an input, APP-SRV-006) in the installed app and the desktop app's test mode, from `dist/` in a copy run from source — answering any other path outside `/api` and `/images` with its `index.html`; when a copy run from source has no build in `dist/`, it shall answer `/` with a plain-text note that the API is running and how to get the page (`npm run dev`, or `npm run build` and start again).
- [x] **APP-SRV-004**: Once its start-up work is done (APP-SRV-001), the server shall serve the app built — the API with its JSON limit and error handlers, `/images`, and the page — by one function, `createApp`, that neither listens, connects to the sim nor loads data when called, and that the server and the API tests both use.
- [x] **APP-SRV-005**: The server shall listen only on 127.0.0.1, in every mode — the installed app, the desktop app's test mode, a copy run from source and the test servers — never on another interface or on `localhost`'s IPv6 address.
- [x] **APP-SRV-006**: When the server bundled for the desktop app starts (the installed app, the desktop app's test mode), the system shall take its data folder, program folder (laid out as `page/`, holding the page build with its `index.html`, beside `airports.csv`, `runways.csv` and their `.downloaded` download times), port, backups folder, sim argument and whether airport downloads are on only from its start-up arguments (`--data`, `--program`, `--port`, `--backups` or `--backups-documents`, `--sim`, `--airport-downloads`), with the logbook to offer (`--offer`) and the fresh-run argument (`--fresh-run`) when given, and, if any but those last two is missing, write "Cannot start: no <input> given" and exit with code 1, never falling back to a default or reading an environment variable for any of them; the sim mode `--sim` gives is live-tracking's (LIVE-LINK-012).
- [x] **APP-SRV-007**: When a copy run from source starts (`npm run dev`, `npm run dev:sim`, `npm start`, the browser-test server), the system shall take each input its start-up arguments (APP-SRV-006) leave out from these defaults: the database `CAREER_DB` when set, else the repository's `data/career.db`, its folder being the data folder; the page from `dist/` and no seed airport lists; port `PORT`, else 3080; the data folder's `backups` folder as the backups folder; airport downloads on; no logbook to offer and no fresh-run argument — its sim mode, with `--sim` given or left out, being live-tracking's (LIVE-LINK-013; a sim on another PC, LIVE-LINK-002).
- [ ] **APP-SRV-008**: The server shall find every file it reads or writes — the page, the seed airport lists, the database, uploaded icons, the airport lists and backups — through its inputs (APP-SRV-006, APP-SRV-007), never through a path worked out from the location of its own code other than a copy run from source's defaults, so the same code runs from source and bundled into one file by esbuild (desktop distribution).
- [x] **APP-SRV-009**: While the server's start-up work is under way (its start-up step other than `done`, APP-SRV-001), the system shall serve, from a start-up stand-in that loads no module holding the server's own database connection (APP-SRV-010), the page's own files, uploaded icons and `/api/status`, apply the request checks (APP-API-011, APP-API-012), and answer every other `/api` request with 503, `Retry-After: 1` and `{"error": "MSFS Career Map is starting (<step>)"}`, handing every request to the app `createApp` builds (APP-SRV-004) once that work is done.
- [ ] **APP-SRV-010**: The system shall run the start-up work's opening, recovery, backup, upgrade and swap of the logbook off the server's event loop, in a worker thread with a database connection of its own, and load the modules that hold the server's own database connection only once that work is done, so `/api/status` keeps answering within 1 s while it runs.
- [x] **APP-SRV-011**: When the server is started with the fresh-run argument (`--fresh-run`, which the desktop shell gives a run's server starts until one has done its start-up work), the system shall pass it to the tracker as the tracker restores its checkpoint (live-tracking, LIVE-CASUAL-015: starting with casual mode off whatever the checkpoint holds), before setting its start-up step to `done`.
- [ ] **APP-SRV-012**: When the server starts airports' monthly refresh of the airport lists (APT-DATA-003), the system shall hand it a check — this server's sim link connected, or the tracker holding a leg in progress (LIVE-SAVE-003), both from live-tracking's status — and tell it whenever either changes, so the refresh waits (APT-DATA-004) without airports reading the tracker.
- [x] **APP-SRV-013**: If the server cannot listen because its port is in use, then it shall write "Port <port> is already in use" and exit with code 10; if Windows refuses it the port (`EACCES`, an excluded port range), then it shall write "Windows refuses port <port>" and exit with code 11; in neither case shall it try another port.
- [ ] **APP-SRV-014**: If the server cannot start — an input missing (APP-SRV-006), a data folder it cannot create or write, a database it cannot open, a data folder another server holds (APP-DATA-008), a logbook it could not back up before upgrading it (APP-BAK-010) — then it shall write the reason as its last error line and exit with code 1, leaving the logbook unchanged.
- [ ] **APP-SRV-015**: Once its start-up work is done, the server shall exit on its own only when shut down (APP-SRV-016, APP-SRV-018), to finish bringing in a logbook (code 12, APP-IMP-003), or on an error outside its request handlers (APP-SRV-020).
- [ ] **APP-SRV-016**: When the server is asked to shut down over the private channel (`{type: "shutdown"}`, which the desktop shell sends only when the app is set to quit, APP-SRV-022), at any point of its start, the system shall, in this order: stop taking samples and stop the sim link with no disconnect reaching the tracker (live-tracking, LIVE-LINK-011); switch casual mode off (LIVE-CASUAL-013); write the tracker's final checkpoint (LIVE-SAVE-005); stop any airport-data work (APT-DATA-025) and abandon any backup or logbook copy under way, deleting its unfinished file; close its event streams and stop listening; checkpoint and close the database; remove the data folder's lock (APP-DATA-007); and exit with code 0 — skipping the steps its start has not reached, finishing a swap of the logbook under way (APP-IMP-004) and letting an upgrade under way roll back (APP-DATA-005) — exiting within 5 s of the request whether or not every step has finished.
- [x] **APP-SRV-018**: When a copy run from source receives a stop signal — SIGINT (Ctrl+C), SIGBREAK (Ctrl+Break) or SIGHUP (its console window closed), or SIGTERM on a system that delivers it — the system shall shut down as APP-SRV-016 orders but leave casual mode as it is (live-tracking, LIVE-CASUAL-011, LIVE-CASUAL-013: a copy run from source has no app to quit).
- [x] **APP-SRV-019**: When the server is asked over the private channel to save the tracker's state (`{type: "save", id}`, APP-SRV-022, as Windows asks whether the session may end and as the PC suspends), the system shall have the tracker write its checkpoint (live-tracking, LIVE-SAVE-004), changing nothing else, and answer `{type: "saved", id}` with the request's id once it is written, answering at once while the tracker has not yet restored its checkpoint.
- [x] **APP-SRV-020**: If an error escapes the server's request handlers — an uncaught exception or an unhandled rejection — then the system shall write it out with its stack and exit with code 1 at once, without a final save (the tracker's last checkpoint holding the leg); an error inside a request handler shall be answered as APP-API-001 says while the server keeps running.
- [x] **APP-SRV-021**: The server shall write its log only to its output and error streams, keeping no log file of its own in the data folder or anywhere else (the installed app's desktop shell keeps them in `server.log`).
- [ ] **APP-SRV-022**: Where the server runs with a private channel (the Electron utility process's own message channel, which only the desktop shell holds), the system shall act on only three requests on it, each an object with a `type` — `{type: "backup", id, kind, version}` (APP-BAK-001), `{type: "save", id}` (APP-SRV-019) and `{type: "shutdown"}` (APP-SRV-016) — repeating in every answer the `id` of the request it answers, writing any other message to its output and otherwise ignoring it, and offer neither saving the tracker's state on request nor shutting down over HTTP.
- [ ] **APP-SRV-023**: When a Vitest test file builds the app with `createApp` (the test servers), the system shall take its inputs as a copy run from source given no start-up arguments does (APP-SRV-007) — the database from `CAREER_DB` (the file's own data folder, APP-RUN-013), the data folder's `backups` folder as the backups folder, and its sim mode from `TRACKER_FAKE` as live-tracking gives it (LIVE-LINK-013), a `PORT` that is not a port number giving the default port rather than an error — with airport downloads off through a parameter of the airport preparation the shared setup runs; take no lock (APP-DATA-007); report in `/api/status` the start-up step `done` from the start, and `airportData` and `ready` as that preparation leaves them; and, once it accepts a logbook to bring in (APP-IMP-003), leave the shutdown that follows to the test that built it, so the test's process goes on.

## Data and Database

- [x] **APP-DATA-001**: The system shall keep its database as `career.db` in the data folder it was given (APP-SRV-006) — in a copy run from source, at `CAREER_DB` when set, else `data/career.db` (APP-SRV-007) — creating the data folder and its `images` folder when missing, with write-ahead logging and foreign keys enforced.
- [x] **APP-DATA-002**: The system shall keep uploaded aircraft icons in an `images` folder, and the OurAirports lists as `airports.csv` and `runways.csv`, in the data folder of the database in use, so a database in another folder (a copy named by `CAREER_DB`, a test's own data folder) never reads or changes another logbook's icons or lists.
- [x] **APP-DATA-003**: When the server opens a database, the system shall create any missing table and add any missing column to an existing table in place, keeping the data already there.
- [ ] **APP-DATA-004**: When the server opens a database that already holds the app's tables, the system shall decide, once the logbook has its id (APP-DATA-006, APP-BAK-011) and before the schema step changes anything, whether the schema step (APP-DATA-003) would add a table or a column, counting only that as a schema upgrade, and a new database or one already current as none.
- [ ] **APP-DATA-005**: The system shall run the schema step (APP-DATA-003) as one transaction, so an upgrade cut short — by a shutdown, a crash or an error — leaves the database as it was.
- [ ] **APP-DATA-006**: When the server's start-up work opens a logbook that holds the app's tables and either has no logbook id (created by an earlier version) or holds a `backup_icons` table (a restored backup or a logbook brought in, APP-BAK-011), the system shall, before deciding whether opening it is a schema upgrade (APP-DATA-004), write a new logbook id — 16 random lowercase hexadecimal characters — to the `settings` table under `logbook_id`, creating that table first in a logbook from before it had one; and when it creates a database, it shall write a new id once the schema step has created it — so no two live logbooks share an id, and the backup before an upgrade (APP-BAK-010) is named with the id the logbook keeps.
- [x] **APP-DATA-007**: While a server started as a process runs (the installed app, the desktop app's test mode, a copy run from source; never the test servers, APP-SRV-023), the system shall hold its data folder with a lock file beside the database (`career.db.lock`) naming the server's process id and port — created exclusively once the server listens, taken over when it is stale, and removed when the server shuts down — and shall take a folder whose lock is held that way, and not stale, as one a server still runs on. A lock is stale when its process no longer runs, when its port refuses the connection or nothing listens on it, when its `/api/status` answers naming another app, another process id or another data folder, or when it names the server's own process; a lock whose process runs and whose port accepts the connection but has not answered within 2 s is not stale. Two spellings of one folder (a junction, a short name, a substituted drive) name the same data folder.
- [x] **APP-DATA-008**: If, when a server started as a process starts (the installed app, the desktop app's test mode, a copy run from source), a server that is not stale holds its data folder's lock (APP-DATA-007), then the system shall write "Another MSFS Career Map server (process <pid>, port <port>) is using this data folder" and exit with code 1 without opening the database.
- [ ] **APP-DATA-009**: The system shall change a logbook's schema only by adding tables and columns, never removing, renaming or retyping one, so a server older than the logbook's schema (an older release run on a logbook a newer one upgraded) opens it without changing it and leaves what it does not know as it is.

## Backups

- [ ] **APP-BAK-001**: When the desktop shell asks over the private channel for a backup (`{type: "backup", id, kind, version}`, APP-SRV-022), naming its kind — `"daily"`, `"update"` before an update with `version` the version about to install, or `"quit"` at the installer's or uninstaller's `--quit` — the system shall back the logbook up into the backups folder (APP-BAK-006), sending `{type: "backup-progress", id}` at least every 2 s while it copies, and then answer `{type: "backup-done", id, file}` with the backup's full path, or `{type: "backup-failed", id, short, reason}` with the short and full reasons (APP-BAK-008), each answer carrying the request's id.
- [ ] **APP-BAK-002**: When `POST /api/backups` is called (the page's **Back up now**, APP-UI-037) once the server's start-up work is done (APP-SRV-009), the system shall back the logbook up into the backups folder (APP-BAK-006) as the pilot's own copy and answer 201 with `{"file": name}`, or the failure's status with `{"error": reason, "short": short}`, the full and short reasons (APP-BAK-008).
- [ ] **APP-BAK-003**: When the system backs the logbook up, it shall copy the open database with SQLite's online backup into a temporary file in the destination folder, add to that copy a `backup_icons` table holding each uploaded icon file the logbook's aircraft rows name (FLEET-LOOK-006) — always, empty when no aircraft row names one, since the table marks a restored backup (APP-BAK-011) — and give the file its name (APP-BAK-004, APP-BAK-009) only once it is complete, deleting the temporary file of a backup that fails or is abandoned.
- [ ] **APP-BAK-004**: The system shall name each backup it takes into the backups folder `career-<yyyyMMddTHHmmssZ>-<kind>-<logbook id>.db` — the UTC time the backup started, its kind (`daily`, `quit`, `manual` for **Back up now**, `update-<version>` before an update to that version, `upgrade-<version>` before an upgrade by that version) and the id of the logbook it holds (APP-DATA-006) — judging which backups are newest by that time, and shall start no backup whose name is already taken until the next second.
- [ ] **APP-BAK-005**: The system shall take backups one at a time, in the order asked for, take a backup the private channel asks for during its start-up work (APP-BAK-001) once that work is done, and hold a backup asked for while a logbook is being brought in (APP-IMP-003), leaving it unanswered if the server exits to finish bringing that logbook in.
- [ ] **APP-BAK-006**: When the system takes a backup, it shall use the backups folder as given: a literal path (`--backups` — the desktop app's test mode, a copy run from source given it — or the default of a copy run from source and the test servers, APP-SRV-007, APP-SRV-023), created with its parents when missing; or Windows' Documents known folder and a path under it (`--backups-documents`: the installed app), Documents looked up through Windows' known folders at that backup — **Back up now** and the backup before an upgrade included — creating only the given path under a Documents folder that exists, and failing because the Documents folder does not exist (APP-BAK-008, its full reason naming that folder) rather than creating Documents.
- [ ] **APP-BAK-007**: When a backup into the backups folder is done, the system shall delete, of that folder's backups named with the same logbook id (APP-BAK-004), the `daily` ones beyond the seven newest and the others — `quit`, `update-…` and `upgrade-…`, the newest `upgrade-…` one left out of the count — beyond the three newest, never deleting a `manual` backup, the newest `upgrade-…` backup, a backup named with another logbook's id, or a file whose name is not a backup's.
- [ ] **APP-BAK-008**: If a backup fails, then the system shall give two reasons: a short reason naming no folder, in fixed words by cause — "Windows refused the write (Controlled folder access?)" for a write refused with `EPERM` or `EACCES`, "the disk is full" for a full disk, "the Documents folder does not exist" for a missing Documents folder (APP-BAK-006), and "the backup failed" for any other failure — and a full reason, "<short reason> — <folder>: <error message>", naming the folder and the error; and it shall carry both in the private channel's `backup-failed` answer (APP-BAK-001) and in `POST /api/backups`'s error (APP-BAK-002).
- [ ] **APP-BAK-009**: If a backup before an update naming version V, or a backup before an upgrade by version V, cannot be written to the backups folder, then the system shall take it into the data folder instead, as `career.before-update-V.db` or `career.before-V.db`, deleting the earlier backup of that pattern in the data folder once it is done, so one of each is kept.
- [ ] **APP-BAK-010**: When the server's start-up work finds that opening the logbook is a schema upgrade (APP-DATA-004), the system shall, with its start-up step `backing-up`, back the logbook up as `upgrade-<the server's own version>`, named with the id the logbook carries after APP-DATA-006 and APP-BAK-011 (into the data folder when the backups folder cannot be written, APP-BAK-009), and only then, with its step `upgrading`, run the schema step; if that backup fails both ways, then it shall leave the logbook unchanged, write "Could not back up the logbook before upgrading it: <full reason>" (APP-BAK-008) and exit with code 1.
- [ ] **APP-BAK-011**: When the server's start-up work opens a logbook holding a `backup_icons` table, empty or not (a restored backup: one copied in by hand as the README's restore says, or a logbook brought in, APP-IMP-003), the system shall, before deciding whether opening it is a schema upgrade (APP-DATA-004), move the data folder's `images` folder, when there is one, aside as `images.before-restore-<yyyyMMddTHHmmssZ>`, write the table's icons into a new `images` folder, and then, in one transaction, give the logbook a new id (APP-DATA-006) and drop the table — doing all of this again at the next start when a start is cut short before the table is dropped — so the restored rows show their own icons and none of the replaced logbook's.

## Bringing In a Logbook

- [ ] **APP-IMP-001**: When `GET /api/logbook/offer` is called, the system shall answer, while the logbook in use holds no hops, its aircraft count and the logbooks it can bring in — the folder given as the logbook to offer (`--offer`) when it holds `career.db`, and the newest backup in the backups folder of each logbook id other than its own whose logbook holds hops, worked out at that moment — each with its folder or file name, the backup's time, its hop count and the date of its newest hop; while the logbook holds hops, that nothing can be brought in; and either way the outcome of the last attempt to bring one in (APP-IMP-005).
- [ ] **APP-IMP-002**: When `POST /api/logbook/import` names a folder, or a backup by its file name in the backups folder, to bring in, the system shall refuse it with 409 and the reason when the logbook in use holds hops, the folder is the data folder in use or holds no `career.db`, a server still runs on that folder ("Close the MSFS Career Map running on that folder first", APP-DATA-007), or the tracker cannot read that logbook's checkpoint ("Log or discard its waiting legs in the other copy first, or update MSFS Career Map", live-tracking, LIVE-SAVE-009).
- [ ] **APP-IMP-003**: When the system accepts a logbook to bring in (APP-IMP-002), it shall pause tracking (live-tracking, LIVE-LINK-017: the sim link stopped with no disconnect reaching the tracker, LIVE-LINK-011, and no sample or sim event taken), copy that logbook with SQLite's online backup into `career.db.incoming` beside the database, add to the copy the uploaded icons its aircraft rows name as a backup does (APP-BAK-003; a backup brought in carries its own), write into it the merged tracker state (LIVE-SAVE-008: this logbook's leg in progress and waiting legs kept, the other logbook's added), mark it complete in `career.db.incoming.json`, answer 202 saying whether the server will be started again by itself (a private channel present) or must be started again by hand, and shut down as APP-SRV-016 orders with casual mode left as it is, exiting with code 12 (a test server leaving that shutdown to its test, APP-SRV-023); if any step before the answer fails, it shall delete the copy, resume tracking (LIVE-LINK-017: the sim link started again on the sim link) and answer the failure.
- [ ] **APP-IMP-004**: When the server starts and finds beside the database a copy marked complete (APP-IMP-003), the system shall, with its start-up step `bringing-in` and before it opens the logbook for its start-up work, check whether the logbook in use holds hops, closing it with its write-ahead log checkpointed into the database; discard the copy when it holds hops by then; and otherwise swap, each step a rename, in this order — the database's `-wal` and `-shm` files, when there are any, aside, then the database itself aside as `career.before-import-<yyyyMMddTHHmmssZ>.db` (the two files keeping that name with `-wal` and `-shm` added), then the copy into place as the database in use (`career.db`) — so an interruption at any step leaves either logbook whole and no write-ahead log beside a database it does not belong to. When it finds a copy marked complete with no database and no `-wal` or `-shm` file beside it (a swap cut short after the database was moved aside), it shall rename the copy into place; and it shall delete a copy that is not marked complete.
- [ ] **APP-IMP-005**: When the server's start-up work brings a logbook in or discards its copy (APP-IMP-004), the system shall keep the outcome — brought in, or not brought in because the logbook in use held hops by then — and report it in `GET /api/logbook/offer` until the next attempt.

## API Conventions

- [x] **APP-API-001**: When an API request fails with a known error, the system shall answer with that error's status and `{"error": message}`; when it fails otherwise, the system shall log the error and answer 500 with its message.
- [x] **APP-API-002**: Once the server's start-up work is done (APP-SRV-009), when an unknown path under `/api` is requested, the system shall answer 404 `{"error": "not found"}`.
- [x] **APP-API-003**: Once the server's start-up work is done (APP-SRV-009), when an API path carries an id that is not a positive whole number, the system shall answer 400 "invalid id".
- [ ] **APP-API-004**: When `GET /api/status` is called, in every mode — the installed app, the desktop app's test mode, a copy run from source, the test servers — the system shall answer 200 with `ok: true`, `app: "msfs-career-map"`, `version` (APP-API-005), `pid` (the server's process id), `dataFolder` (absolute), `logbookId` (the logbook's id, APP-DATA-006, the id its backups are named with, APP-BAK-004), `sim` (`"link"`, `"fake"` or `"off"`), `startup` (`"opening"`, `"bringing-in"`, `"backing-up"`, `"upgrading"` or `"done"`), `airportData` (APP-API-010), `ready` (APP-API-009) and the airport and runway counts `airports` and `runways` — `logbookId`, `airports` and `runways` null until the logbook is open (the test servers reporting `startup` `done` from the start, APP-SRV-023).
- [ ] **APP-API-005**: The system shall take the app version from `package.json` — read at start by a copy run from source, built into the server bundle by the desktop build and into the page's build — report it in `GET /api/status`, and send `MSFSCareerMap/<version> (+https://github.com/SharpWave/msfs-career-map)` as the User-Agent on every request the server makes to an outside service (OurAirports, aviationweather.gov, Wikipedia, Open-Meteo, SimBrief), naming the project, never a person, as the contact.
- [x] **APP-API-006**: When an API call from the page fails, the page shall report the server's `error` message, or the HTTP status and its text when there is none; a 204 answer shall count as success with no content.
- [x] **APP-API-007**: When an API call from the page fails, the page's request helper shall raise an error that carries the HTTP status and the answer's parsed body alongside the message.
- [ ] **APP-API-008**: The system shall answer `GET /api/status` from the moment it listens, from what it holds in memory and without reading the database — its start-up step set to `opening` before it listens, the logbook's id kept in memory once the start-up work has given or read it (APP-DATA-006), and the airport and runway counts kept in memory once the logbook is open and after each airport import.
- [ ] **APP-API-009**: The system shall report `ready: true` in `GET /api/status` only once its start-up step is `done` and airport preparation at start has ended, succeeded or failed (APT-DATA-021, APT-DATA-022), `ready: false` until then, and `ready: true` from then on for as long as the server runs, while a preparation a daily check repeats (APT-DATA-022) is under way included.
- [ ] **APP-API-010**: The system shall report airport preparation (airports, APT-DATA-021) in `GET /api/status` as `airportData`: its `state` — `"waiting"` until the start-up work is done, then `"seeding"`, `"downloading"`, `"importing"`, `"done"` or `"failed"` — with the `list` (`"airports"` or `"runways"`) while downloading or importing, the `rows` imported so far and the list's `total` while importing, and the `error` once it has failed; when a daily check repeats a failed preparation (APT-DATA-022), the repeated preparation's report shall replace the earlier one's from the moment it starts.
- [x] **APP-API-011**: If a request reaches the server with a `Host` header whose host name is neither `127.0.0.1` nor `localhost`, or with none, then the system shall answer 403 and act on nothing, in every mode (a guard against another site's page reaching the server through a host name that resolves to this PC).
